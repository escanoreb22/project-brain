# Research policy

Research only when a fact is unavailable locally or is reasonably time-sensitive. Prefer local manifests, lockfiles, generated API specs, vendor SDK source, and project configuration before the web.

## Source order

1. Official specification or vendor documentation for the installed version.
2. Official release notes, migration guide, security advisory, or maintained source repository.
3. Primary standards body or research paper.
4. Reputable secondary material only for ecosystem comparison or user sentiment.

For competitor UX and user feedback, distinguish official product behavior from reviews and anecdotes. Record URL, title, publisher, publication/update date, access date, version scope, claim, and evidence class: `verified`, `owner_statement`, `inferred`, or `unknown`.

Never:

- claim compatibility from a current-version page when the project uses an older version;
- copy an example before checking prerequisites, signatures, permissions, limits, retries, and deprecation status;
- use search snippets as final evidence;
- treat popularity as security or maintenance proof;
- send project secrets, proprietary code, personal data, or customer data to search or third-party tools.

When sources disagree, report the disagreement and prefer the source matching the installed version. Keep citations near the decision record; do not paste entire documentation pages into project memory.
